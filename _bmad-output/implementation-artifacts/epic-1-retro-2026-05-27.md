## What Went Well

- Monorepo, local infrastructure, backend, frontend shell, auth, role access, and plant-scope foundation are all in place.
- Local infrastructure was validated with Docker Compose for PostgreSQL, pgAdmin, Redis, InfluxDB, EMQX, and WAHA.
- Backend verification matured through Maven tests, MockMvc, and Testcontainers where persistence/schema behavior mattered.
- Frontend verification included check/build/lint and browser evidence for responsive shell, auth flow, role UX, and plant scope selector states.
- Story 1.7 improved evidence discipline by explicitly mapping acceptance criteria to automated or browser evidence.

## Challenges

- Security and validation issues drove most review churn across auth, role access, and plant scope.
- Repeated findings involved JWT safety, timing-oracle behavior, CSRF/CORS policy, safe error shape, ObjectMapper ownership, and permission/loading states.
- Some evidence statements initially overstated production coverage where only foundation contracts existed.
- Frontend authorization/loading states needed more care to avoid showing unrestricted placeholder content before effective scope loaded.

## Key Lessons

1. Security behavior crosses layers, so happy-path acceptance criteria are not enough.
2. Validation needs layered proof: DTO validation, service/domain invariant, and database constraints.
3. Permission features need explicit `401`, `403`, empty, loading, and out-of-scope evidence.
4. Foundation contracts must not be described as full operational enforcement until real domain endpoints adopt them.
5. API contract generation and TanStack Query should start with Epic 2 to avoid broad frontend retrofit later.

## Decisions Captured

### TanStack Query starts in Epic 2

Yusuf confirmed TanStack Query should start in Epic 2 because Syncro is multi-phase and delaying server-state structure would create too much retrofit work.

Implications:

- Domain CRUD should use query hooks instead of ad-hoc component fetches.
- Query keys must account for active plant scope from the beginning.
- Manual fetch remains acceptable only for shell/session boundary code.

### Orval baseline goes into Story 2.1

Yusuf confirmed Springdoc/OpenAPI + Orval should be included in Story 2.1, not handled as separate prep.

Implications for Story 2.1:

- Add Springdoc OpenAPI baseline in backend.
- Add Orval config in frontend.
- Generate TanStack Query hooks for Plant API.
- Use generated client/hooks in Plant CRUD UI.
- Keep generated files isolated from handwritten code.
- Do not duplicate Plant API types by hand.
