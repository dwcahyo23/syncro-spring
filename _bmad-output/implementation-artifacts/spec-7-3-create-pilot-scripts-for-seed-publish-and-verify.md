## Intent

**Problem:** Epic 7 must run the end-to-end pilot without manual guesswork, but today every step is a hand-copied command: the 7-1 seed header documents the hardened psql apply command, 7-2 delivers wire fixtures at `syncro/tests/fixtures/`, and the consumer contract (publish file body verbatim, refresh only `timestamp`, keep `messageId` verbatim) lives only inside the 7-2 spec prose. Stories 7-4/7-5/7-6/7-7 all need the same four repeatable actions (seed, publish before-threshold, publish threshold, verify evidence) and have no scripted, documented, Windows-PowerShell-native way to run them. Compounding this, the 3-13 EMQX security layer is deny-by-default and its seeded example device `device_BF-08410_GM1` is only allowed to publish to `factory/BF-08410/GM1/telemetry` — plant/machine INVERTED relative to the backend topic grammar (`TelemetryTopic.parse`: segment 1 = plantCode, segment 2 = machineCode), so no existing MQTT credential can publish the pilot payload to the canonical topic `factory/GM1/BF-08410/telemetry`, and the host has no MQTT client installed at all (`mosquitto_pub`/`mqttx` absent).

**Approach:** Four Windows PowerShell scripts at the architecture-pinned paths `syncro/scripts/seed-pilot.ps1`, `publish-jbf19-before-threshold.ps1`, `publish-jbf19-threshold.ps1`, `verify-pilot.ps1` (architecture.md directory tree names all four exactly; "Dev Script Expectations" lists seed / publish ×2 / verify telemetry / verify alert / verify WAHA job). `seed-pilot.ps1` wraps EXACTLY the 7-1 review-hardened apply flow (stdin pipe into `docker compose --env-file <env> -f syncro/infra/docker-compose.yml exec -T postgres sh -c 'PGCLIENTENCODING=UTF8 psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'` — in-container env expansion, atomic BEGIN/COMMIT) with the Windows-PowerShell 5.1 UTF-8 pipe guard that live testing proves is load-bearing for the `·` label (verified: normalized md5 identical WITH the guard, corrupted WITHOUT it). The publish scripts implement the 7-2 consumer contract through the EMQX Management API (verified live against the running EMQX 6.2.2): `POST /api/v5/login` with the dashboard credentials docker-compose already maps from `SYNCRO_MQTT_USERNAME`/`SYNCRO_MQTT_PASSWORD` → JWT bearer → `POST /api/v5/publish` (qos 1, retain false) with the fixture body after a regex refresh of only `timestamp` — zero host tooling, zero hardcoded secrets, all connection values from `syncro/.env`. `verify-pilot.ps1` checks pilot state through the same in-container psql pattern (seed rows, `machine_counter_states`, `sparepart_alerts`, `notification_jobs`, `telemetry_quarantine` diagnostics) plus `redis-cli` latest-hash evidence, interprets expectations from the current counter state, and prints operator/technical evidence pointers. One small infra correction accompanies the scripts: the 3-13 example device is corrected to the canonical `device_GM1_BF-08410` → `factory/GM1/BF-08410/telemetry` (CSV + entrypoint ACL + README) so the documented real-device path finally matches the backend grammar; the scripts themselves do not depend on it.

## Boundaries & Constraints

**Always:**
- Exact script paths fixed by the epics Story 7.3 AC and the architecture.md tree (lines 984-988): `syncro/scripts/seed-pilot.ps1`, `syncro/scripts/publish-jbf19-before-threshold.ps1`, `syncro/scripts/publish-jbf19-threshold.ps1`, `syncro/scripts/verify-pilot.ps1`. All four start with `$ErrorActionPreference = 'Stop'` and PowerShell comment-based help (`.SYNOPSIS`/`.DESCRIPTION`/`.EXAMPLE`/`.NOTES`) documenting prerequisites, idempotency/dedupe behavior, and Windows PowerShell 5.1+ compatibility — this satisfies "scripts are documented for Windows PowerShell".
- Every script resolves its own paths from `$PSScriptRoot` (script lives in `syncro/scripts/`, so the syncro root is `Split-Path -Parent $PSScriptRoot`) and accepts an `-EnvFile` parameter defaulting to `syncro/.env` — the same env file docker-compose consumes. No absolute paths, no CWD assumptions.
- `seed-pilot.ps1` wraps the 7-1 apply command VERBATIM (in-container `sh -c` so `$POSTGRES_USER`/`$POSTGRES_DB` expand inside the container from the compose environment; `PGCLIENTENCODING=UTF8`; `-v ON_ERROR_STOP=1`; the seed's own `BEGIN; ... COMMIT;` provides atomicity). Do NOT invent a different mechanism (no `psql -f` copy-in, no `docker compose cp`, no host-shell env sourcing). The one deliberate addition over the seed-header text: the script invokes `docker compose --env-file $EnvFile -f $ComposeFile exec ...` with absolute resolved paths (the `validate-syncro-baseline.ps1` precedent) so it works from any CWD — the header's bare `docker compose -f ...` form relies on CWD auto-discovering `syncro/.env`; the in-container `sh -c` payload itself stays byte-identical.
- UTF-8 pipe guard is mandatory in `seed-pilot.ps1`: `$OutputEncoding = New-Object System.Text.UTF8Encoding($false)` + `Get-Content -Raw -Encoding UTF8 $SeedFile` before piping into `docker compose exec -T`. Live evidence: Windows PowerShell 5.1's default `$OutputEncoding` (ASCII) mangles the seed's nine UTF-8 `·` bytes (normalized md5 mismatch `e14ef79f...` vs `6b6b9d9b...`); with the guard the piped content is byte-identical. Check `$LASTEXITCODE -eq 0` after the pipe and fail loudly otherwise.
- `seed-pilot.ps1` preflight: verify Flyway migrations are applied before seeding — `... exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -t -A -c "SELECT count(*) FROM flyway_schema_history WHERE success;"'` (verified working in-container without a password — local trust; returns 30 on the current local DB). Zero rows or a psql error (relation does not exist) → terminate with actionable guidance: boot the backend once against the stack or run `mvn -f syncro/apps/backend/pom.xml flyway:migrate` (mirrors the seed header's Preconditions). Post-apply: print a canonical-row summary (counts for plant GM1, group Forming, machine BF-08410/ACTIVE, sparepart `BF-08410GM1ELEPLCWEC000`, installation 1000/0/90, 3 users, 3 responsibilities by level) via the same in-container psql pattern so re-runs visibly show `INSERT 0 0`-style stability.
- Publish scripts implement the 7-2 recorded consumer contract exactly: publish the fixture FILE BODY as the MQTT message body to `factory/GM1/BF-08410/telemetry`; refresh ONLY `timestamp` with the current UTC instant at publish time — `"(Get-Date).ToUniversalTime().ToString(\"yyyy-MM-dd'T'HH:mm:ss'Z'\", [System.Globalization.CultureInfo]::InvariantCulture)"` (ISO-8601, no fractional seconds — `Instant.parse`-compatible), applied as a targeted regex replace on the RAW file text (`'"timestamp"\s*:\s*"[^"]*"'` → `'"timestamp": "<now>"'`) so every other byte (especially `messageId` `pilot-jbf19-before-threshold-890` / `pilot-jbf19-threshold-900`) stays verbatim; no JSON re-serialization of the payload (PS 5.1 `ConvertTo-Json` would reformat/escape). A `-NoTimestampRefresh` switch publishes the file fully verbatim (7-2 documents stale-timestamp effects: historical-looking Influx point, skewed latency indicator — the switch exists for exact-duplicate evidence runs, not the default flow).
- Publish transport = EMQX Management API on the local broker (verified live on the running `emqx/emqx:6.2.2`): (1) `POST http://{SYNCRO_MQTT_HOST}:{SYNCRO_MQTT_DASHBOARD_PORT}/api/v5/login` with `{"username": SYNCRO_MQTT_USERNAME, "password": SYNCRO_MQTT_PASSWORD}` (docker-compose maps these exact env keys to `EMQX_DASHBOARD__DEFAULT_USERNAME/PASSWORD`) → `.token`; (2) `POST .../api/v5/publish` with `Authorization: Bearer <token>` and body `@{ topic=$Topic; payload=$bodyText; qos=1; retain=$false } | ConvertTo-Json`. QoS 1 matches the backend subscription (`MqttSubscriptionConfig` adapter `setQos(1)`); `retain` false (payload contract has no retained semantics). Dashboard basic auth does NOT work for POST (live-probed: 401 `BAD_API_KEY_OR_SECRET`) — the login/JWT flow is required. `emqx ctl` has NO publish subcommand in 6.2.2 (full 248-line help verified) — do not attempt it.
- Publish scripts load `syncro/.env` into the process environment using the `start-backend.ps1` parsing idiom (`Get-Content | ForEach-Object { if ($_ -match '^([^#=][^=]*)=(.*)$') { ... } }`) and read `SYNCRO_MQTT_HOST` (default `localhost`), `SYNCRO_MQTT_DASHBOARD_PORT` (default `18083`), `SYNCRO_MQTT_USERNAME`, `SYNCRO_MQTT_PASSWORD` (no defaults for credentials — missing values terminate with "check syncro/.env" guidance, satisfying "environment variables/config, not hardcoded secrets"). Pass `-UseBasicParsing` on web calls (no-op on PowerShell 7, avoids the IE first-run dialog on 5.1). Assert the publish response echoes the topic and contains the fixture's `messageId` (runtime guard against any encoding mangling), then print messageId, `counting`, and the refreshed timestamp.
- Both publish scripts print the follow-up contract: run `verify-pilot.ps1` next; republishing the same fixture within the Redis dedupe window (default PT30S, key `syncro:machine:{machineId}:telemetry:dedupe:{messageId}`) produces the `mqtt_telemetry_duplicate` log line — intentional evidence for 7-5's duplicate-publish AC; after the window, the alert-level non-RESOLVED dedup guard and the notification-job idempotency key keep a republish harmless.
- `verify-pilot.ps1` reads state ONLY through the established in-container exec patterns: `docker compose --env-file <env> -f syncro/infra/docker-compose.yml exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -t -A -c "<sql>"'` and `... exec -T redis redis-cli --raw HGETALL syncro:machine:{machineId}:latest` (redis runs without auth in the local compose; both patterns live-verified). Resolve the machine UUID by natural key — `SELECT m.id FROM machines m JOIN plants p ON p.id = m.plant_id WHERE p.code = 'GM1' AND lower(m.code) = 'bf-08410'` — never assume the seed's fixed UUID (the seed adopts pre-existing case-variant rows).
- `verify-pilot.ps1` sections and verdict semantics (each line prints PASS / FAIL / INFO, script exits non-zero only on FAIL): (1) PREFLIGHT — postgres `SELECT 1` and redis `PING` hard-fail; EMQX `GET /api/v5/status` (public, no auth — live-verified 200) and backend `GET http://localhost:8080/api/v1/health` are warn-only (persisted evidence outlives broker/backend restarts). (2) SEED — canonical row counts per 7-1. (3) TELEMETRY — `machine_counter_states.counting`/`updated_at` for BF-08410 (this row is saved on EVERY accepted persist — `TelemetryPersistenceService.persist` calls `counterStateRepo.save` unconditionally after the latest write), Redis latest hash fields (`counting`, `countingDelta`, `receivedAt`, `traceId`) with the PT5M TTL caveat (absent hash ≠ missing telemetry; counter state is the durable authority), and `telemetry_quarantine` as a diagnostic (count > 0 → FAIL printing the latest `rejection_reason`/`rejection_field`/`topic` — a quarantined publish is the fastest root-cause path). (4) ALERT — interpret by counter state: `counting=900` expects exactly one non-RESOLVED `sparepart_alerts` row (status `OPEN`/`ACKNOWLEDGED`/`RESOLVED` lifecycle, `consumed_percentage_snapshot=90.00`, print `trace_id`); `counting=890` expects zero rows (PASS "no alert — correct before-threshold state"). (5) NOTIFICATION — `notification_jobs` for the alert: `escalation_level`, `status` (enum: PENDING, ROUTING_FAILED, SENT, EXHAUSTED, ESCALATED, CANCELLED, RATE_LIMITED), `recipient_phone`, `trace_id`, `error_detail`; placeholder numbers (`6281234567801/02/03`) make PENDING + attempt-failure evidence the expected live-WAHA outcome. (6) ACKNOWLEDGEMENT RESULT — alert status plus per-level job listing (post-ack, STAFF/LEADER jobs must not be SENT after the acknowledgement — 7-6 owns the action; this section reports the state). Finally print operator/technical pointers: Machine Hub `/dashboard/master-data/machines/BF-08410`, telemetry dashboard, alerts, system health (web dev server assumed at `http://localhost:3000`), pgAdmin explicitly labeled "local/dev evidence tool only, not a product feature", and the optional Influx query `docker compose exec -T influxdb influxdb3 query --token "$INFLUXDB3_ADMIN_TOKEN" --database syncro "SELECT * FROM telemetry ORDER BY time DESC LIMIT 5"` (measurement `telemetry` per `InfluxTelemetryWriter.toPoint`; CLI syntax live-verified).
- Infra correction (3-13 follow-up, required): `syncro/infra/emqx/etc/auth-bootstrap.csv` device row becomes `device_GM1_BF-08410,Device@Mqtt#2026!Dev,false` (same committed dev-placeholder password pattern as the row it replaces — DW-46 documents the accepted dev convention); `docker-entrypoint.sh` ACL block for the device upserts `{"username":"device_GM1_BF-08410","rules":[{"topic":"factory/GM1/BF-08410/telemetry","action":"publish","permission":"allow"}]}` and its comments/examples are corrected to "machine BF-08410 in plant GM1"; `infra/emqx/README.md` current-rules table gets the corrected device row AND the stale `syncro_backend → factory/#` entry corrected to `factory/+/+/telemetry` (the 3-13 review decision tightened it; the README was never updated). ## Design Notes

- **Why the Management API publish and not an MQTT client:** the host has no MQTT client (`mosquitto_pub`/`mqttx` absent — checked), `emqx ctl` in EMQX 6.2.2 has no publish subcommand (full help enumerated), and pulling a helper container/image or requiring a host install would violate the no-new-tools rule and add fragility. The Management API path was verified live against the running broker: `/api/v5/status` is public; dashboard-basic-auth POSTs fail with 401 `BAD_API_KEY_OR_SECRET`; `POST /api/v5/login` with the compose-mapped dashboard credentials returns a JWT; `POST /api/v5/publish` with the bearer token reaches real validation (`topic_name_invalid` on empty topic, qos validation error) — endpoint and auth confirmed without publishing anything. This path is pure `Invoke-RestMethod`, env-driven, and exercise-neutral: the backend subscriber receives management-API publishes exactly like device publishes (same topic/QoS-1 delivery), so 7-4/7-5 evidence is unaffected. The real-device path remains available and is what the corrected `device_GM1_BF-08410` example now documents — for manual parity testing with any MQTT client an operator chooses to install.
- **Why the seed wrap must stay byte-exact:** the 7-1 review hardened the apply command specifically to (a) expand `$POSTGRES_USER`/`$POSTGRES_DB` INSIDE the container (host expansion reads nothing), (b) abort atomically via `ON_ERROR_STOP` + the file's `BEGIN/COMMIT`, and (c) force UTF-8 for the `·` label. The only Windows-specific hazard left is the PowerShell pipe encoding, which this spec closes with the live-tested guard: WITHOUT it, Windows PowerShell 5.1 pipes ASCII and corrupts the seed's nine `·` characters (18 UTF-8 bytes across 3 lines — normalized md5 `6b6b9d9b...` vs correct `e14ef79f...`); WITH it the piped content is byte-identical. The post-apply summary doubling as a visible label check gives the operator a tripwire even if the guard is ever removed.
- **The 3-13 ordering bug and why this story fixes it:** `TelemetryTopic.parse` reads `factory/{plantCode}/{machineCode}/telemetry` (segment 1 = plant, segment 2 = machine — source-verified), and the canonical pilot data is plant `GM1` / machine `BF-08410`. The 3-13 example (`device_BF-08410_GM1` → `factory/BF-08410/GM1/telemetry`, README "machine GM1 in plant BF-08410") inverts both, so following the README against the pilot data publishes to a topic the backend rejects as `unknown_plant` (quarantined). The fix follows 3-13's own documented convention `device_{plantCode}_{machineCode}` → `factory/{plantCode}/{machineCode}/telemetry`, which for the pilot yields `device_GM1_BF-08410` → `factory/GM1/BF-08410/telemetry`. Kept small (CSV row + entrypoint block + README rows) and decoupled from the scripts: bootstrap CSV credentials load only on first data-volume creation (README-documented EMQX behavior), while ACL rules upsert on every container start — so a running stack gets the corrected rule on restart but keeps the old credential until manually added/removed; fresh stacks get both. The Management-API scripts work regardless, which is why they don't gate on it.
- **Evidence model of `verify-pilot.ps1`:** every check reads state the production pipeline already persists — `machine_counter_states` (saved unconditionally on each accepted persist), `sparepart_alerts` (V19, partial unique index `WHERE status != 'RESOLVED'` backs the "exactly one active alert" expectation), `notification_jobs` (V24, `UNIQUE (alert_id, escalation_level)` backs the no-duplicate-job expectation), `telemetry_quarantine` (fastest failure root-cause), and the Redis latest hash (5-minute TTL — treated as best-effort, with the durable counter state as authority). Expectations are keyed to the observed counter value (890 → no alert; 900 → one alert) so the script is correct at every pilot stage instead of assuming 7-5 already ran. Placeholder WhatsApp numbers mean PENDING/ROUTING_FAILED-with-attempt-evidence is the expected live-WAHA outcome until real numbers are set (seed header caveat) — reported as evidence, not failure.
- **Why threshold publish is verified backend-stopped:** a live threshold publish with the backend running would create the alert + TECHNICIAN job that story 7-5 must prove from a known state; with `cleanSession(true)` (3-1 config, DW-23/DW-61 documented) a stopped backend simply never receives the message, so the mechanics check (login → publish → 200 echo) is safe. The before-threshold publish IS run end-to-end here: counting=890 telemetry with no alert is precisely 7-4's invariant, and re-publishing in 7-4 is harmless (dedupe window expired; counter math unaffected).
- **Scope fences inherited from 7-1/7-2:** no `docs/pilot-validation.md` (7-7 will reference these scripts), no `tests/e2e/` specs, no `PilotFixture.java`/`pilot-fixture.json` (still no second code consumer — the scripts read the committed fixture files directly, keeping `syncro/tests/fixtures/` the single source of wire truth), no changes to seed/fixtures/production code. The scripts are deliberately "boring": plain PowerShell, docker compose exec patterns already established by the 7-1 apply command and `validate-syncro-baseline.ps1`, and web calls with the `start-backend.ps1` env idiom.
- **Grounding note (web research):** none required — every technical fact is pinned to repo source or a live probe executed at spec time (EMQX 6.2.2 endpoints/auth behavior, `emqx ctl` capabilities, PowerShell 5.1 pipe encoding md5 evidence, in-container psql/redis-cli/influxdb3 CLI syntax, running-stack status, local DB state: Flyway 30/30, seed applied, alerts table empty). No new libraries, versions, or external APIs are introduced.
